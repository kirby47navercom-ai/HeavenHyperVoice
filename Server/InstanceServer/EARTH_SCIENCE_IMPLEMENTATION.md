# HeavenHyperVoice 인스턴스 지구과학 구현

## 1. 구현 목적

이 시스템은 인스턴스 던전마다 서로 다른 날씨를 서버에서 계산하기 위해 만들었다.
클라이언트가 비나 눈의 발생 여부를 정하지 않는다. `InstanceServer`가 방의 기온,
습도, 기압, 구름, 강수, 바람과 지표 상태를 계산하고 같은 방의 플레이어에게 동일한
결과를 보낸다.

현재 목표는 전 지구 기후를 계산하는 연구용 모델이 아니다. 졸업작품의 방 구조에 맞춰
다음 조건을 만족하는 작은 물리 모델을 사용한다.

- 방마다 독립된 날씨 상태를 가진다.
- 사람이 없는 방은 계산하지 않는다.
- 물은 수증기, 구름, 비·눈, 지표수와 토양 사이를 이동한다.
- 계산 결과는 모든 클라이언트에 같은 값으로 전달한다.
- 낮밤 순환과 화면 밝기는 날씨 계산에 포함하지 않는다.

## 2. 코드 구성

| 파일 | 역할 |
|---|---|
| `src/InstanceWeather.h` | 기후 설정, 전송용 결과, 방 하나의 날씨 상태 정의 |
| `src/InstanceWeather.cpp` | 증발, 혼합, 응결, 강수, 적설, 침투 계산 |
| `src/RoomManager.h/.cpp` | 방마다 날씨 객체를 소유하고 플레이어가 있을 때 진행 |
| `src/World.h/.cpp` | 방 전체에 같은 날씨 패킷을 방송 |
| `src/main.cpp` | 인스턴스 종류별 기후 설정을 읽어 `InstanceType`에 저장 |
| `../Protocol/field.fbs` | 서버가 클라이언트에 보내는 `WeatherState` 정의 |
| `../Protocol/FieldCodec.h` | 날씨 결과를 FlatBuffers 패킷으로 직렬화 |
| 클라이언트 `HHVFieldConnection.*` | `WeatherState` 패킷을 언리얼 구조체로 복사 |
| 클라이언트 `UEFieldServerBridgeComponent.*` | 게임 스레드에서 블루프린트 이벤트 발생 |

서버 계산 흐름은 다음과 같다.

```text
서버 실행 옵션
  → InstanceType.weather
  → 새 Room 생성
  → Room.weather.initialize()
  → RoomManager 틱
  → InstanceWeather.advance()
  → snapshot()
  → WeatherState 패킷
  → 클라이언트 OnInstanceWeatherChanged
```

## 3. 인스턴스 종류별 기후 설정

`InstanceWeatherProfile`은 방이 시작될 때 사용할 기후 기준이다.

| 변수 | 단위 | 의미 |
|---|---:|---|
| `meanTemperatureC` | °C | 기단이 장기적으로 가까워지는 평균 기온 |
| `initialRelativeHumidityPct` | % | 방 생성 직후 저층 공기의 상대습도 |
| `meanPressureHpa` | hPa | 기압 변화의 중심값 |
| `initialSurfaceWaterKgM2` | kg/m² | 처음 지표에 놓인 물의 질량, 1kg/m²는 물 1mm |
| `initialSoilWaterKgM2` | kg/m² | 처음 토양에 저장된 물 |
| `gameSecondsPerRealSecond` | 배율 | 현실 1초에 진행할 날씨 시뮬레이션 시간 |

서버 실행 시 `--instance-weather`를 반복해서 종류별 값을 준다.

```text
--instance-weather type=tempC,humidityPct,pressureHpa,surfaceWater,soilWater,timeScale
```

예를 들어 1번 인스턴스를 습한 숲처럼 시작하려면 다음과 같이 실행한다.

```text
--instance-weather 1=18,82,1013.25,4,16,60
```

2번 인스턴스를 차갑고 눈이 남기 쉬운 지역으로 만들 수도 있다.

```text
--instance-weather 2=-4,88,1005,1,10,60
```

설정하지 않은 타입은 `InstanceWeatherProfile`의 기본값을 사용한다. 등록되지 않은 맵
타입을 지정하거나 값의 범위를 벗어나면 서버가 시작 단계에서 오류를 낸다. 잘못된 기후
설정으로 서버가 조용히 실행되는 일을 막기 위한 검사다.

## 4. 방마다 날씨가 다른 이유

`Room` 구조체가 `InstanceWeather weather`를 직접 가진다. 따라서 같은 인스턴스 타입이라도
방이 다르면 상태를 공유하지 않는다.

초기화할 때 `type`과 `roomId`를 섞어 난수 씨앗을 만든다. 같은 숲 기후를 사용하는 방도
초기 온도, 습도, 기압, 구름물이 조금씩 달라진다. 난수 씨앗은 방 번호로 고정되므로 같은
입력에서 결과를 다시 추적할 수 있다.

## 5. 대기와 지표 상태

한 방은 현재 평균 기단 한 칸으로 계산한다. 대기는 저층과 상층 두 층이며, 지표는 물과
토양, 눈과 얼음을 가진다.

### 저층 대기 `nearAir`

- 플레이어가 체감하는 기온과 습도를 저장한다.
- 지표에서 증발한 수증기를 먼저 받는다.
- 과포화된 액체 물방울은 안개에 해당한다.

### 상층 대기 `upperAir`

- 저층보다 낮은 온도를 가진다.
- 구름물과 강수의 원천을 저장한다.
- 구름물이 임계량을 넘으면 비나 눈이 내려간다.

### 지표 `ground`

- `waterKgM2`: 지표수와 빗물
- `soilKgM2`: 토양에 스며든 물
- `snowKgM2`: 쌓인 눈
- `iceKgM2`: 얼어 있는 지표수
- `temperatureC`: 비와 눈, 융해와 결빙을 구분하는 지표 온도

## 6. 시간 진행

`advance(realDeltaSeconds)`는 서버의 현실 경과 시간을 받는다. 한 프레임이 오래 멈춰도
최대 5초까지만 받아 큰 폭주를 막는다. 여기에 `gameSecondsPerRealSecond`를 곱한 뒤
10초짜리 고정 단계로 나눠 `simulateStep()`을 호출한다.

고정 단계를 사용하는 이유는 서버 틱 간격이 흔들려도 계산 순서와 결과가 갑자기 크게
달라지지 않게 하기 위해서다. 기본 배율 60에서는 현실 1초가 날씨 시간 60초다.

## 7. 기온, 기압과 바람

낮밤 순환 대신 느리게 이동하는 기단 전선을 사용한다. 방마다 다른 `weatherPhase`가 있어
모든 방이 동시에 같은 기온과 기압으로 움직이지 않는다.

현재값은 다음 형태로 목표값에 가까워진다.

```text
새 값 = 현재값 + (목표값 - 현재값) × 반응 비율
반응 비율 = 1 - exp(-경과시간 / 반응시간)
```

저층 기온, 상층 기온, 지표 온도와 기압은 서로 다른 반응시간을 사용한다. 기압의 현재값과
목표값 차이가 커질수록 풍속이 증가한다. 바람 방향은 방의 초기 위상과 시뮬레이션 시간으로
서서히 회전한다.

## 8. 포화 수증기와 상대습도

공기가 가질 수 있는 수증기량은 온도에 따라 달라진다. 포화 수증기압은 FAO 형태의 식을
사용한다.

```text
포화수증기압(kPa) = 0.6108 × exp(17.27 × T / (T + 237.3))
```

현재 수증기 질량을 증기압으로 바꿀 때는 수증기의 기체상수 `461.5J/(kg·K)`와 층 깊이를
사용한다. 현재 수증기량을 포화량으로 나눈 값이 상대습도다.

## 9. 물 순환 계산 순서

한 고정 단계는 다음 순서로 실행된다.

### 9.1 증발

지표의 포화수증기압과 저층 공기의 현재 수증기압 차이를 구한다. 차이가 클수록 지표수가
수증기로 더 많이 이동한다. 지표수가 없으면 토양 수분이 토양의 젖은 정도에 비례해 더
느리게 증발한다.

### 9.2 저층·상층 혼합

두 대기층의 수증기 농도 차이를 계산한다. 농도가 높은 층에서 낮은 층으로 물을 이동해
연직 혼합을 표현한다. 이 과정은 물을 새로 만들거나 없애지 않는다.

### 9.3 응결과 재증발

수증기가 온도에 따른 포화량을 넘으면 초과분을 액체 물방울로 바꾼다. 포화량보다 적고
이미 액체 물방울이 있으면 다시 수증기로 돌아간다. 저층 액체는 안개, 상층 액체는 구름에
해당한다.

### 9.4 비와 눈

상층 구름물이 임계량을 넘으면 일부가 지표로 내려온다. 저층 기온이 낮을수록 눈의 비율이
증가한다. 눈은 적설 저장소로, 비는 지표수 저장소로 이동한다.

### 9.5 융해와 결빙

지표가 영상이면 눈과 얼음이 녹아 지표수가 된다. 영하면 지표수 일부가 얼음으로 이동한다.

### 9.6 침투와 배수

지표수는 토양의 빈 용량만큼 스며든다. 토양 수분이 포장용수량을 넘으면 초과분이 천천히
배수된다. 배수량은 방 밖으로 빠져나간 물로 별도 누적한다.

## 10. 물 보존 확인

초기화할 때 대기, 구름, 지표수, 토양수, 눈과 얼음의 총량을 저장한다. 스냅샷을 만들 때
현재 총물과 누적 배수를 합쳐 초기값과 비교한다.

```text
물수지 오차 = 현재 총물 - 초기 총물 + 누적 배수
```

증발, 응결, 비와 눈은 저장소 사이의 이동이므로 총량을 바꾸지 않는다. 이 값이 0에서 크게
벗어나면 계산 중 물이 생성되거나 사라졌다는 뜻이다. 서버는 이 값을 클라이언트에도 보내
디버깅할 수 있게 한다.

## 11. 서버 비용을 줄이는 방법

`RoomManager`는 플레이어가 한 명 이상 있는 방만 `weather.advance()`로 진행한다. 날씨
결과는 초당 한 번만 방송한다. 이동 스냅샷처럼 초당 여러 번 보내지 않아 같은 값을 반복
전송하지 않는다.

현재 방 하나의 날씨는 저층, 상층과 지표 한 세트만 계산한다. 플레이어마다 계산하거나
맵 전체를 수백 개 셀로 나누지 않으므로 인스턴스 수가 늘어도 부담이 작다.

## 12. 클라이언트로 보내는 값

| 값 | 단위/범위 | 용도 |
|---|---:|---|
| `temperature_c` | °C | 비·눈 구분, 입김과 환경 표현 |
| `relative_humidity_pct` | % | 안개와 습한 공기 표현 |
| `pressure_hpa` | hPa | 기압 상태와 디버깅 |
| `cloud_cover` | 0~1 | 구름 양과 하늘 밝기 |
| `precipitation_mm_per_hour` | mm/h | 비·눈 입자 강도 |
| `wind_speed_mps` | m/s | 입자와 식생 흔들림 |
| `wind_direction_degrees` | 0~360° | 바람 방향 |
| `ground_wetness` | 0~1 | 젖은 지면 머티리얼 |
| `snow_depth_m` | m | 적설 표현 |
| `water_balance_error_kg_m2` | kg/m² | 물 보존 검증 |

클라이언트는 이 값을 다시 계산하지 않는다. 실제 서버 환경에서는 받은 값을 화면 연출에만
사용한다. 이 원칙으로 같은 방에 있는 모든 플레이어가 같은 날씨를 보게 한다.

## 13. Yang2 로컬 실행

Yang2는 서버를 띄우지 않고 기능을 확인하기 위한 브랜치다. Yang2 전용 구현 파일이
`InstanceWeather.cpp`를 클라이언트 모듈에서 직접 한 번 컴파일한다. 복사한 날씨 코드를
따로 유지하지 않으므로 main의 서버 계산식이 변경된 뒤 main을 Yang2로 가져오면 같은
수식이 로컬 시험에도 적용된다.

Yang2 브릿지는 서버 연결 대신 로컬 `InstanceWeather`를 만들고 틱에서 `advance()`를
호출한다. 결과는 실제 서버 패킷이 도착했을 때와 같은 `OnInstanceWeatherChanged` 이벤트로
보낸다. 화면과 블루프린트는 서버 결과인지 Yang2 로컬 결과인지 구분하지 않아도 된다.

이 클라이언트 권위 경로는 Yang2 전용이다. `YANG2_CLIENT_AUTHORITY_ONLY` 표식이 들어간
파일과 빌드 설정은 main에 병합하지 않는다.

## 14. 현재 범위와 확장 조건

현재는 방 전체가 하나의 평균 날씨를 공유한다. 졸업작품의 “인스턴스마다 다른 날씨”에는
이 구조가 맞는다. 같은 방 안에서 산 정상과 계곡의 날씨를 다르게 해야 할 때만 공간 격자를
추가한다.

다음 기능은 현재 게임 요구에 없으므로 넣지 않았다.

- 전 지구 대기와 해류 계산
- 판 구조론, 침식과 지질 변화
- 수백 개 공간 셀의 3차원 유체 계산
- 낮밤 순환과 천체 위치 계산
- 독립 EarthScience 프로그램의 GUI

포켓몬 출현과 전투 시스템이 날씨 규칙을 실제로 사용하게 되면 서버가 이미 가진 기온,
강수, 풍속 값을 그 규칙의 입력으로 연결한다. 사용처가 생기기 전에는 별도의 생태 시뮬레이터를
서버에 추가하지 않는다.
